# 开发维护规则

## 项目记忆规则

本项目依赖文档保存长期上下文。

每次开发或讨论后，如果出现以下变化，必须更新文档：

- 新增平台
- 新增店铺
- 新增数据类型
- 改变目录结构
- 改变文件命名规则
- 改变登录方式
- 改变导出流程
- 发现平台页面变化
- 确认无数据判断方式
- 修复重要问题
- 增加或调整配置项

## 文档维护位置

核心文档位于：

```text
docs/
```

当前文档：

- `README.md`：项目总览
- `requirements.md`：需求规格
- `platform-rules.md`：平台导出规则
- `file-rules.md`：文件与目录规则
- `development-rules.md`：开发维护规则
- `development-log.md`：开发日志

## 开发原则

第一阶段优先跑通拼多多，不同时开发多个平台。

实现时应保持平台适配器结构，避免把拼多多逻辑写死到全局流程里。后续天猫、抖音、快手、京东应能按同样任务模型扩展。

工具应先保证稳定可恢复，再追求完全自动化。

## 安全和合规原则

工具只模拟用户本人在平台后台的正常操作。

工具不得：

- 破解验证码
- 绕过短信验证
- 绕过扫码登录
- 绕过平台权限
- 抓取用户无权访问的数据
- 使用非授权接口
- 保存店铺账号密码

遇到验证时，工具应暂停等待人工处理。

## 建议代码结构

后续正式开发时，建议结构如下：

```text
config/
  shops.yaml
  tasks.yaml
docs/
src/
  main.py
  app/
    config.py
    dates.py
    logging.py
    downloads.py
    runner.py
  platforms/
    pinduoduo.py
  ui/
    ...
exports/
  原始数据/
```

具体结构可以根据实际开发语言和框架调整，但必须保留清晰的平台适配层。

## 配置原则

店铺、平台、数据类型、保存路径等业务信息应尽量放在配置文件中，不要写死在代码里。

建议配置包含：

- 平台名称
- 店铺名称
- 登录配置
- 数据类型
- 是否启用
- 是否必需
- 输出文件名
- 页面入口

## 验证原则

每次修改导出逻辑后，至少验证：

- 能计算正确的上个月日期。
- 能创建正确目录。
- 能记录成功、无数据、失败三种状态。
- 单个任务失败后，后续任务仍能继续。
- 文件不会误覆盖。

正式接入平台页面后，还需要验证：

- 登录状态复用。
- 人工验证码后能继续。
- 下载文件能正确识别。
- 文件能被现有报表工具读取。
