# 平台导出规则

## 通用平台规则

工具应将平台导出流程抽象为任务。

每个任务至少包含：

- 平台
- 店铺
- 数据类型
- 日期范围
- 后台入口
- 查询动作
- 导出动作
- 无数据判断方式
- 下载文件识别方式
- 输出文件名
- 任务结果

工具运行时应允许用户选择任务范围。任务范围包括：

- 店铺范围
- 数据类型范围
- 日期范围

第一版至少要支持选择数据类型和日期范围。店铺范围可以默认全部店铺，后续再增加选择部分店铺。

## 登录和验证规则

工具优先复用 Edge 登录状态，不应频繁退出登录再重新登录。

如果平台要求扫码、短信验证码、滑块或其他人工验证，工具应暂停并提示用户处理。用户完成验证后，工具继续执行。

工具不得尝试破解验证码、绕过平台风控或绕过账号权限。

## 店铺切换规则

优先使用平台后台自带的店铺切换能力。

如果多个店铺必须使用不同账号登录，第一阶段允许人工介入登录。后续可为每个账号保存独立浏览器用户数据目录，降低重复验证概率。

拼多多第一阶段的 9 个店铺是分别登录的，无法在后台直接切换。拼多多实现时应按店铺账号分别维护登录状态或浏览器用户数据目录。

拼多多 9 个店铺按 9 套独立账号密码处理，每个店铺都是独立账号。

第一版运行时需要支持选择店铺，默认全选 9 个店铺，也允许用户只选择单个或部分店铺执行。

账号和登录状态规则：

- 不保存账号密码。
- 每个店铺使用独立浏览器用户数据目录保存登录状态。
- 首次运行或登录失效时，用户手动完成登录和验证码。
- 工具检测到已登录后继续执行导出任务。
- 工具不得自动退出当前店铺账号再登录其他店铺账号。

## 无数据规则

默认情况下，每个店铺、每个被选择的数据类型都应检查一次。

没有数据不是失败。工具应记录状态为“无数据”，并记录查询月份、平台、店铺和数据类型。

如果某个数据类型本次没有被用户选择，工具不应执行该任务。

如果某个数据类型需要生成固定结构工作簿，即使某个店铺或某个 TAB 无数据，也应保留对应 sheet，并只写入表头，保证后续汇总工具读取结构稳定。

## 日期拆分规则

平台或数据类型可能对查询日期范围有限制。

如果用户选择的日期范围超过某个数据类型允许的最大范围，工具应自动拆分成多个子任务。

示例：某数据类型单次最多查询 7 天，用户选择 2026-05-01 至 2026-05-21，则工具应拆分为：

- 2026-05-01 至 2026-05-07
- 2026-05-08 至 2026-05-14
- 2026-05-15 至 2026-05-21

拆分后的多个文件或多段网页数据应能合并或分别保存，具体方式按数据类型规则确定。

## 失败处理规则

单个导出任务失败时，不应中断整个平台全部任务。

工具应记录失败原因，并继续执行后续任务，除非遇到无法继续的全局问题，例如浏览器无法启动、平台完全无法访问、账号被强制下线且无法人工恢复。

建议失败原因分类：

- 未登录
- 需要验证码
- 权限不足
- 页面元素未找到
- 查询失败
- 导出按钮不可用
- 下载超时
- 文件识别失败
- 未知错误

## 拼多多规则

### 第一阶段数据类型

拼多多第一阶段需要导出：

- 退货数据
- 消费者负向体验扣款数据
- 延迟发货数据
- 客服绩效数据

### 拼多多任务策略

每个拼多多店铺只执行用户本次选择的数据类型。

如果用户选择全部数据类型，则每个店铺执行以下任务：

1. 查询指定日期范围内的退货数据。
2. 如果有数据，点击导出，并到已生成报表页下载文件；如果无数据，记录无数据。
3. 查询指定日期范围内的消费者负向体验扣款数据。
4. 如果有数据，采集网页表格并保存；如果无数据，记录无数据。
5. 查询指定日期范围内的延迟发货数据。
6. 如果有数据，分别导出延迟发货、缺货、虚假发货/虚假轨迹 3 个 TAB，并整合为一个工作簿；如果无数据，记录无数据。
7. 进入客服数据页的客服绩效数据 TAB，选择指定日期范围并下载客服绩效表单。

### 拼多多退货数据规则

后台菜单路径：

```text
后台首页 -> 左侧菜单栏 -> 售后管理 -> 售后工作台
```

退货数据有平台导出按钮。

导出后不会直接完成下载，需要进入已生成报表页下载生成好的报表文件。

页面区域：

- 快速筛选订单：投诉预警、待处理即将逾期、待商家处理、待举证即将逾期、待商家举证、买家催处理、平台处理中、待买家处理、退货待处理等快捷入口。
- 售后搜索：可输入订单编号、物流单号、商品 ID、售后编号，批量导出时默认留空。
- 高级查询：需要展开高级查询区域后设置筛选条件。

第一版退货数据筛选条件：

| 字段 | 取值 |
| --- | --- |
| 批量查询 | 默认留空 |
| 售后类型 | 退款退货 |
| 售后状态 | 退款成功 |
| 售后原因 | 默认不选 |
| 发货状态 | 已发货 |
| 操作类型 | 默认不选 |
| 退款金额 | 默认留空 |
| 售后申诉 | 默认不选 |
| 申请时间 | 用户选择的开始日期 00:00:00 至结束日期 23:59:59 |
| 快递拦截 | 默认不选 |
| 极速退款 | 默认不勾选 |
| 纠纷退款 | 默认不勾选 |

查询和导出流程：

1. 展开高级查询。
2. 设置售后类型、售后状态、发货状态和申请时间。
3. 点击右侧“查询”按钮。
4. 判断结果数量，示例中 `全部(1203)` 表示有 1203 条。
5. 点击“批量导出”。
6. 弹窗标题为“批量导出报表”。
7. 弹窗中核对查询条件和售后单数。
8. 点击“确认生成”。
9. 点击页面上的“查看已生成报表”。
10. 在“近30个已生成报表”弹窗中找到生成成功的记录。
11. 点击该记录操作列的“导出”下载文件。

当前自动化实现优先走接口，页面流程作为规则来源和人工兜底：

| 步骤 | 接口 |
| --- | --- |
| 查询数量 | `/mercury/mms/afterSales/queryList` |
| 生成报表 | `/mercury/mms/afterSales/applyExcelReport` |
| 轮询报表列表 | `/mercury/mms/afterSales/queryExcelExportList` |
| 获取签名下载地址 | `/mercury/mms/afterSales/queryExcelReportUrl` |

接口筛选条件与页面一致：售后类型为退款退货、售后状态为退款成功、发货状态为已发货，申请时间为用户选择的开始日期 00:00:00 至结束日期 23:59:59。

已生成报表弹窗字段：

- 序号
- 生成时间
- 操作人
- 查询条件
- 售后单数
- 操作

生成成功判断：

- 已生成报表弹窗中生成时间列显示“生成成功”。
- 操作列出现“导出”链接。
- 生成中时生成时间列显示“生成中”。
- 生成中时操作列的“导出”为灰色不可点击。
- 生成成功后操作列的“导出”会变为蓝色可点击。
- 页面会动态更新生成状态，不需要手动刷新弹窗。
- 报表生成时间取决于数据量，通常 30 秒以内。

无数据判断：

- 查询结果数量显示为 `全部(0)`。
- 批量导出按钮变为灰色不可点击。
- 列表中间显示 `暂无售后单`。
- 右下角显示 `共有 0 条`。

已确认补充：

- 下载后的文件格式为 XLSX。
- 自动化保存文件名固定为 `YYYYMMDD-YYYYMMDD + 店铺短名 + 退货.xlsx`，不使用平台随机文件名。

### 拼多多消费者负向体验扣款数据特殊规则

后台菜单没有开放入口权限，需要直接打开 URL 进入：

```text
https://mms.pinduoduo.com/aftersales/customer_complain_appeal
```

消费者负向体验扣款数据与普通导出不同：

- 查询范围单次最长只能选择 7 天。
- 30 天前的数据会清空，无法查询。
- 页面没有导出按钮。
- 第一版应通过采集网页表格数据实现，模拟用户当前“复制粘贴”的人工方式。
- 采集结果格式必须尽量保持用户当前手动复制粘贴得到的格式，因为后续已有自动汇总工具依赖该格式。
- 示例文件已提供：`示例/4月拼多多负向体验4.1-4.30.xlsx`。
- 示例按店铺分 sheet，后续生成结果也必须按店铺分 sheet。
- sheet 名必须沿用示例中的店铺短名。
- 字段列和复制出来的多行结构要保持与示例一致。

示例中的 sheet 名：

1. 拼多多金喆
2. 拼多多逸观
3. 拼多多大雁
4. 拼多多大雁母婴玩具
5. 拼多多大雁母婴
6. 拼多多大雁书籍
7. 拼多多大雁童书
8. 拼多多逸观母婴玩具
9. 拼多多逸观书籍

示例中的表头固定为：

| 列序号 | 字段名 |
| ---: | --- |
| 1 | 订单编号 |
| 2 | 商品信息 |
| 3 | 问题类型 |
| 4 | 补偿金额（元） |
| 5 | 扣款进度 |
| 6 | 创建时间 |
| 7 | 处理状态 |
| 8 | 操作 |

示例保留了网页复制后的多行结构。单条记录通常会占用多行，例如：

- 第一行包含订单编号、问题类型、补偿金额、扣款进度、创建时间、处理状态、操作等字段。
- 后续行在“商品信息”列保存商品标题、历史整改建议、商品 ID 等内容。
- 其他列在后续行中可能为空。

后续采集时不应强行整理为“一条记录一行”，除非用户明确调整报表工具规则。

采集网页表格时仍需要确认：

- 网页复制时是否有隐藏列或动态内容。
- 空数据时是否仍生成对应店铺 sheet。

页面筛选区字段：

| 字段 | 说明 |
| --- | --- |
| 订单编号 | 可输入完整订单编号，批量导出时默认留空 |
| 创建时间 | 日期范围字段，示例显示 `2026-05-01 ~ 2026-05-07` |
| 处理状态 | 下拉框，批量导出时默认选择“全部” |
| 查询 | 点击后按筛选条件刷新列表 |
| 重置 | 清空或恢复默认筛选条件 |

页面 TAB：

- 全部
- 商品问题
- 服务问题

第一版建议采集“全部”TAB 即可，因为该 TAB 包含商品问题和服务问题的汇总数据，并且示例文件也是统一表头结构。

页面表格列：

1. 订单编号
2. 商品信息
3. 问题类型
4. 补偿金额（元）
5. 扣款进度
6. 创建时间
7. 处理状态
8. 操作

分页规则：

- 分页区域位于页面右下角。
- 有数据时显示总条数，例如 `共有 65 条`。
- 页码按钮显示为 1、2、3、4 等，并带上一页、下一页按钮。
- 从 `65 条` 对应 `4` 页判断，页面每页约 20 条。
- 后续采集需要遍历所有页，直到下一页不可点击或页码结束。

无数据判断：

- TAB 数量显示为 `全部 0`、`商品问题 0`、`服务问题 0`。
- 表格中间显示 `暂无申诉记录`。
- 页面右下角显示 `共有 0 条`。

详情页规则：

- 表格操作列有 `查看详情`。
- 第一版暂不进入详情页，优先采集列表页中与示例一致的字段。
- 如果后续发现已有报表工具需要详情页中的字段，再补充详情页采集规则。

如果用户选择的日期范围超过 7 天，工具应自动拆分为多个不超过 7 天的子任务，并将同一店铺多个分段的采集结果合并到该店铺对应 sheet 中。

如果用户选择的日期范围包含 30 天前，工具应提示用户该部分可能无法查询，并在日志中记录。

### 拼多多延迟发货数据规则

后台菜单路径：

```text
后台首页 -> 左侧菜单栏 -> 账户资金 -> 消费者补偿
```

延迟发货数据有平台导出按钮。

页面标题为“消费者补偿”。

页面顶部 TAB 包含：

1. 延迟发货
2. 缺货
3. 虚假发货/虚假轨迹
4. 延迟送达

第一阶段需要导出的 TAB 为：

1. 延迟发货
2. 缺货
3. 虚假发货/虚假轨迹

工具需要对 3 个 TAB 分别执行查询和导出。用户提供的截图覆盖了延迟发货数据大类下的多个 TAB，确认 3 个 TAB 的查询和导出流程基本一致。当前自动化实现优先使用页面接口完成查询、生成报表、轮询导出列表和下载，页面按钮流程作为平台规则参考。

查询条件：

| 字段 | 说明 |
| --- | --- |
| 订单编号 | 默认留空 |
| 补偿时间 | 使用用户选择日期范围；开始时间为 `00:00:00`，结束时间为 `23:59:59` |
| 查询 | 点击后刷新当前 TAB 的查询结果 |

时间说明：

- 页面日期控件需要分别选择开始时间和结束时间，每次选择后都要点击“确认”。
- 自动化接口查询使用北京时间毫秒时间戳。
- 自动化生成报表接口使用平台前端一致的 UTC ISO 字符串，例如北京时间 `2026-04-01 00:00:00` 会发送为 `2026-03-31T16:00:00.000Z`，这是同一时刻而不是日期偏移。
- 下载前必须按导出列表返回的 `punishStartTime` / `punishEndTime` 校验命中记录，校验口径为北京时间 `00:00:00` 至 `23:59:59`。

结果区：

- 标题显示为“补偿记录查询”。
- 结果区显示总数据量，例如 `共查询到 53 条数据`、`共查询到 12 条数据`、`共查询到 32 条数据`。
- 页面提示查询结果最多仅展示 3 万条，大于 3 万条可批量导出查看。
- 右侧有“批量导出”按钮。
- 表格右下角有分页，需按平台导出逻辑而不是手动分页抓取。

无数据判断：

- 查询结果显示 `共查询到 0 条数据`。
- 表格中间显示无数据文案。
- 延迟发货 TAB 示例文案为 `没有查询到相应的补偿记录`。
- 缺货 TAB 示例文案为 `没有查询到相应的数据`。
- 虚假发货/虚假轨迹 TAB 示例文案为 `没有查询到相应的数据`。
- 页面右下角显示 `共有 0 条`。

导出流程：

1. 进入对应 TAB。
2. 设置补偿时间范围。
3. 点击“查询”。
4. 如有数据，点击“批量导出”。
5. 弹窗标题随 TAB 变化，例如：
   - 导出延迟发货补偿订单明细
   - 导出缺货补偿订单明细
   - 导出虚假发货补偿订单明细
6. 弹窗展示补偿时间和订单编号。
7. 弹窗提示为保证查询性能，两次导出的时间间隔需保持在 5 分钟以上。
8. 点击“生成报表”。
9. 点击生成报表后，平台会自动跳转到对应 TAB 的批量导出列表页。
10. 在批量导出列表页点击“下载补偿订单列表”下载 XLSX 文件。


示例文件说明：

- 文件名前缀括号中的文字为用户手动补充的 TAB 类型，方便识别，不属于平台默认文件名。
- 平台默认文件名为随机字符串形式，开发时实际下载确认即可。

三个 TAB 导出字段不完全一致，因此整合时不能强行合并到同一张表。应整合为同一个工作簿的 3 个 sheet，并保留每个 TAB 原始表头。

原始文件保留规则：

- 延迟发货 3 个 TAB 平台原始下载的 XLSX 需要保留，方便后续核对。
- 整合后的工作簿作为报表工具主要读取文件。

### 拼多多客服绩效数据规则

后台菜单路径：

```text
后台首页 -> 左侧菜单 -> 多多客服 -> 客服数据
```

进入页面后选择顶部 TAB：

```text
客服绩效数据
```

页面 URL 参考：

```text
https://mms.pinduoduo.com/mms-chat/overview/service
https://mms.pinduoduo.com/mms-chat/overview/merchant
```

查询区域：

- 页面标题为 `客服数据`。
- 数据区块为 `客服绩效详情`。
- 日期字段位于 `客服绩效详情` 下方，示例显示 `2026-05-01 ~ 2026-05-28`。
- 选择日期并点击日期控件中的 `确认` 后，页面会自动按时间范围刷新，不需要点击查询按钮。
- 日期可选择整月，但平台最多只能选择近 60 天数据；60 天以前日期置灰不可点击。
- 如果用户选择的开始日期超过近 60 天范围，工具应直接标记该店铺客服绩效失败并提示，不自动裁剪日期。

导出规则：

- 导出按钮文字为 `下载表单`，位于客服绩效详情表格右下方。
- 点击后直接下载文件，无弹窗确认，也不进入报表生成列表页。
- 下载文件格式为 XLS。
- 最终文件名固定为 `YYYYMMDD-YYYYMMDD + 店铺短名 + 客服绩效.xls`，例如 `20260501-20260515拼多多大雁书籍客服绩效.xls`。

无数据规则：

- 客服绩效页面不会出现真正的无数据状态。
- 即使没有业绩数据，也会列出所有客服账号，指标显示为 0。
- 因此第一版不需要生成空表兜底，只要下载平台原始 XLS。
